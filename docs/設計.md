# 設計 — 業務ツール統合ランチャー

要件定義書(`business-tools-launcher` 要件)と汎用Webアプリ作成 基盤仕様書に対して、
**何をどう決めたか**と、**なぜそう決めたか**を書きます。

---

## 1. このランチャーの立ち位置

ランチャーは業務ロジックを持ちません。持つのは順序と状態だけです。

```
Windows
   │
   ▼
business-tools-launcher (常駐・tkinter)
   │  ボタンを押す
   ▼
各リポジトリの start.bat を実行
   │
   ▼
GET /api/health が応答するまで待つ   ← ここを飛ばさない
   │
   ▼
ブラウザーを開く
```

各ツールの Python の起こし方は、それぞれのリポジトリの `start.bat` に集約したままにします
(要件定義書 §12.2 / §21)。ランチャーが知っているのは「BATを呼ぶ」ことと「`/api/health` を見る」ことだけです。

### 監視レベル

基盤仕様書 §3 の3段階のうち、**レベル1(通常の操作アプリ)** を選びました。

ランチャー自身は長時間処理も自動実行も持たず、ボタンを受けて起動・停止するだけだからです。
ただし、**起動する相手はレベル2以上**(看板と総合ツールは長時間処理を持つ)なので、
停止のときだけ相手の事情を汲みます — 実行中の処理があれば止めずに知らせ、中断してよいかは利用者が決めます(基盤仕様書 2.8)。

---

## 2. 起動完了の判定

`start.bat` を実行しただけでは起動完了と判断しません(要件定義書 §21)。

判定に使うのは相手の `GET /api/health` です。4つのツールはどれも同じ起動基盤を使っていて、
次の形で応答します。

```json
{
  "app_id": "nlm.nippou-tool",
  "display_name": "日報管理ツール",
  "version": "3.0.0",
  "app_root": "C:\\業務ツール\\日報",
  "port": 8733,
  "pid": 12345,
  "ready": true,
  "stage": "アプリを準備中"
}
```

**`app_id` の一致まで見ます。** HTTPが返るだけでは足りません — 同じポートを別のアプリが
使っていることがあるからです(基盤仕様書 2.3)。`ready` が false のあいだは待ち続け、
`stage` をランチャーバーに出して「進んでいる」ことを見せます(基盤仕様書 2.2)。

> 要件定義書 §7.2 の例は `GET /health` ですが、4リポジトリの実装は `/api/health` です。
> どちらでも動くよう、**確認URLを設定にしました**(`port` + `health_path`、必要なら
> `health_url_override` で丸ごと差し替え)。相手側を書き換えずに済みます。

### PIDとポートは応答から取る

ランチャーが `subprocess` で起こしたのは `cmd.exe` であって、業務ツール本体ではありません。
そのPIDで止めようとしても本体は落ちません。**止めるときに使うPIDは `/api/health` が返した値**です
(要件定義書 §10)。

`start.bat` を起こしたプロセスのPIDも別枠(`launch_pid`)で記録します。
本体が応答しないときの後片付けに使います。

## 3. 安全な停止

要件定義書 §21 が禁じているのは1点、**Pythonプロセス名だけを指定して一括終了しない**ことです。

穏やかな方法から順に試します。

| 順 | 方法 | いつ使うか |
|---|---|---|
| 1 | 相手の `stop.bat` に任せる | いちばん確実。相手の作法で止まる |
| 2 | `POST /api/shutdown` | `stop.bat` が見つからないとき |
| 3 | 記録したPIDで止める | 応答しないときだけ |

`stop.bat` は設定しなくても、**`start.bat` の隣**を既定として拾います。
4つのツールはどれも `start.bat` と `stop.bat` が並んでいるので、設定項目を1つ減らせます。

### PIDで止める前の照合

PIDは使い回されます。記録した時点では日報だったPIDが、止めるころには無関係なプロセスに
なっていることがあります。そこで落とす前に、**そのプロセスのコマンドラインにツールの置き場所が
入っているか**を確かめます。

- 取れないときは **止めません**。誤って別のアプリを落とすより、止まらないほうが害が小さいからです。
  止まらなければ利用者は気づいて手で対処できますが、他人の処理を落とすと気づかれないままデータが失われます。
- 印が短すぎる(`C:\` など)ときも照合しません。どのプロセスにも一致してしまい、照合が形だけになるためです。
- コマンドラインの取得は `wmic` → PowerShell (CIM) の順です。`wmic` は新しい Windows では既定で
  入っていないため、そこだけで諦めると「照合できない=止めない」でツールを終了できなくなります。

### 引き取り待ち(ゾンビ)の扱い

ランチャーは `start.bat` を**自分の子として**起こします。POSIX では、終了した子は親が引き取るまで
PID表に残ります。これを「生きている」と答えると、止まったものを止まっていないと報告し続けます。
`_is_alive()` は `/proc` を見て、引き取り待ちの状態を「終了済み」と答えます。

止めたあとに `cmd.exe` が残った場合は落とします。残すと、見えないコンソールが切り替えのたびに1つずつ増えます。

## 4. 切り替え

```
現在：日報
   ↓  [看板] を押す
日報を終了しています...        ← STOPPING
   ↓  /api/health が応答しなくなるまで待つ
看板を起動しています...        ← STARTING
   ↓  /api/health が app_id 付きで応答するまで待つ
現在：看板                     ← RUNNING
```

順序は `app_manager.ToolManager` が持ちます。要求ごとに番号を振り、**新しい要求が来たら古い待機を
打ち切ります** — 日報の起動を待っている最中に看板を押されたとき、2つの待機が同時に画面を書き換えないためです。

同じツールのボタンをもう一度押したときは起動し直さず、ブラウザーだけを開きます(要件定義書 §9)。

### ランチャー外で動いているツールの引き継ぎ

ランチャーを再起動したときや、利用者が `Start.vbs` から直接ツールを起動していたときは、
「動いているのにランチャーは何も知らない」状態になります。そのままボタンを押すと二重起動です。

起動時に `adopt_running()` が、記録と、設定されている全ツールの `/api/health` を当たって、
動いているものを現在のツールとして引き継ぎます。

## 4.5 ブラウザー画面 (要件定義書 §8.3)

切り替えのときに、そのツールを映している画面だけを閉じる。利用者が別に開いている
Google やメールのタブは閉じない。

### なぜ `webbrowser.open()` を使わないか

`webbrowser.open(url)` は既定のブラウザーへURLを渡すだけで、**開いたタブへの手がかりを
何も返さない**。あとからそのタブだけを閉じる方法が無い。かといって `chrome.exe` の
プロセスを落とすと、Google もメールも道連れになる — §8.3.3 がいちばん避けたい状態そのもの。

### 専用プロファイルのアプリウィンドウ

```
chrome.exe --app=http://127.0.0.1:8733/
           --user-data-dir=%LOCALAPPDATA%\BusinessToolsLauncher\browser\nlm.nippou-tool
           --no-first-run --no-default-browser-check
           --disable-session-crashed-bubble
```

こうすると3つが同時に手に入る。

1. **ランチャー自身の子プロセスになる** → PIDで閉じられる
2. **利用者のふだんのブラウザーとは別インスタンス** — プロファイルが違うので
   ウィンドウもプロセスも共有しない → 落としても通常のタブに手が届かない
3. **タブもアドレスバーも無い1画面** → 業務ツール専用の窓になる

「関係ないタブを閉じない」ことを、後から見分けるのではなく**構造上あり得なくする**のが要点。
その上でさらに、閉じる前にコマンドラインへ専用プロファイルの道が入っていることを照合する
(バックエンドを止めるときと同じ守り方)。

プロファイルは**ツールごとに分ける**。前の窓が閉じきる前に次を起こしたとき、同じプロファイルを
掴み合って新しい窓が既存プロセスに合流し、こちらの手がかりが消えることを避けるため。

探す順は Edge → Chrome → Chromium。Edge はWindowsに必ず入っているので先頭に置いた。
`config/launcher.json` の `browser.preferred` で変えられ、見つけられない置き方をしている端末には
`browser.extra_paths` で実行ファイルを直接指定できる。

### 見つからなかったとき

Chromium系が1つも無い端末では `webbrowser.open()` に落とす。**その場合は閉じられない**ので、
記録に `browser_pid = 0` が残り、画面には「切り替えのときに自動では閉じないので、
不要になったタブは手で閉じてください」と出す。黙って閉じたことにしない。
`start_debug.bat --check` がどちらになるかを表示する。

### 処理順序 (§8.3.2)

```
現在：日報
   ↓ ［看板］を押す
日報の専用ブラウザー画面を閉じる      ← ここが先
   ↓
日報のバックエンドを停止
   ↓
日報の終了を確認
   ↓
看板を起動 → 起動完了を確認
   ↓
看板の専用ブラウザー画面を開く
   ↓
現在：看板
```

画面を先に閉じるのは、逆にすると閉じるまでのあいだ利用者の画面に「接続できません」が
出るため。

### 画面とバックエンドを別々に持つ (§8.3.4)

`Status` は `responding`（バックエンド）と `browser_open`（画面）を別の値として持つ。
利用者が画面だけ手で閉じても、バックエンドは動いたまま — そのことをバーに
`現在：日報（画面は閉じています）` と出す。同じボタンをもう一度押すと、バックエンドは
起動し直さずに画面だけ開く。

`stop.bat` は別プロセスなので、画面のPIDとプロファイルの道も `runtime/current.json` に
書いておく。そうしないとコンソールから画面を閉じられない。

## 5. 設定 (要件定義書 §13 / §14)

端末ごとにリポジトリの置き場所が違うので、`start.bat` のパスはコードに埋め込みません。

```
config/launcher.json   同梱の既定値。初回の投入だけに使う
        ↓ 初回起動
%LOCALAPPDATA%\BusinessToolsLauncher\data\launcher.db   ← 動作中の唯一の参照先
        ↑ 設定画面
```

**既定値に `start.bat` のパスは入れません。** もっともらしいパスを入れると、
「設定したつもりで別の場所を指している」状態を作るためです。空にしておけば設定画面が「未設定」と出します。

管理する項目(要件定義書 §14)と、その持ち方:

| 項目 | 列 | 備考 |
|---|---|---|
| アプリID | `app_id` | 主キー。`/api/health` の照合に使う |
| 表示名 | `display_name` | ボタンの文字 |
| start.batのパス | `start_command` | 設定画面の主役 |
| 作業ディレクトリ | `work_dir` | 空なら `start.bat` の置き場所 |
| 使用ポート | `port` | |
| 起動確認URL | `health_path` / `health_url_override` | ふだんは `port` + `health_path` から組み立てる |
| 停止方法 | `stop_method` | `auto` / `stop_bat` / `shutdown_api` / `pid` |
| 起動引数 | `start_args` | 既定 `--no-browser` |

起動確認URLを2つの列で持っているのは、**出どころを1つに保つ**ためです。
`port` と完成形URLを対等に持つと、ポートを直したのにURLが古いまま、という食い違いが起きます。
ふだんは `port` から組み立て、どうしても違う形が要るときだけ `health_url_override` で差し替えます。

5個目・6個目のツールは行を足すだけで増やせます。使わないツールは `enabled` を落とせば隠せます。

### PCごとのモード (要件定義書 §15)

`pc_settings` テーブルに保存し、設定画面から変更できます。利用者に毎回選ばせません。

**初回起動時の選択ダイアログは作っていません。** §15 は将来要件で、
「詳細なモード内容は各業務ツール側の要件として別途定義する」とあります。
選択肢が決まっていない段階で全端末に選択を強いると、意味のない値が保存されるだけになります。
モードの中身が決まったら、保存と設定画面はそのまま使えます。

## 6. 層の分け方 (基盤仕様書 2.5)

```
Start.vbs / start_debug.bat / stop.bat     利用者の入口
        │
launcher.py            環境確認 → 多重起動判定 → 画面を出す
        │
launcher/ui/           tkinter。**ここだけが画面を知る**
        │
app_manager.py         起動・切り替え・停止の順序と状態
        │
process_manager.py     対象の確認と安全な停止
launcher/health.py     起動確認
launcher/tool_registry.py   設定 (SQLite)
```

画面より下の層は tkinter を読み込みません。`stop.bat` からの停止、CIでの試験、
tkinter の入っていない端末のいずれでも動かせるようにするためです。
`tests/test_no_tkinter.py` が構文木を見てこれを固定しています。

`launcher.py` だけは例外で、起動前の確認と失敗の通知にダイアログを使います。
`Start.vbs` はコンソールを出さないので、そこで伝えないと「何も起きない」ようにしか見えません。

## 7. 現場で踏みやすいところ

### 自分自身への通信にプロキシを通さない

`urllib` の既定は環境変数や Windows のインターネット設定からプロキシを拾います。
社内PCではたいていプロキシが入っており、除外一覧に `127.0.0.1` が無いと
**自分自身への通信までプロキシへ送られて失敗します**。相手ツールは待ち受けているのに
応答が返らず、時間切れで「起動できませんでした」になります。

`launcher/health.py` の送信口は `ProxyHandler({})` を明示的に挟んでプロキシを外しています。
起動に失敗したときは、いま効いているプロキシ設定も画面に出します。

### BAT末尾の `pause` で固まらせない

診断用のBATは末尾に `pause` を置くことがあります。ランチャーから呼ぶとコンソールが見えないので、
そのままでは永久に待ち続けます。子プロセスの標準入力を `DEVNULL` にすると、`pause` はすぐ抜けます。

### ツールの出力はファイルへ逃がす

`subprocess.PIPE` で受けてはいけません。業務ツールはランチャーが生きているあいだ動き続けるので、
誰も読まないパイプはやがて詰まり、ツールごと固まります。
`logs/tool_<アプリID>.out.log` へ追記すれば詰まらず、調査の材料にもなります。

### 起動できないときに何を出すか

時間切れの一言だけでは、次に何を見ればよいか分かりません。場合分けして出します。

| 状況 | 出すもの |
|---|---|
| `start.bat` が先に終了した | 戻り値。起動引数を疑う案内 |
| ポートは待ち受けているが応答しない | プロキシ設定と起動確認URL |
| 何も起きない | 待った秒数と起動確認URL |

どの場合も、ツールの出力ログとランチャーのログの場所を添えます。

### 起動ファイルの文字コード

`.bat` は cmd.exe が**コンソールのコードページ**で、`.vbs` は WSH が**システムANSI**で読みます。
日本語Windowsではどちらも CP932 です。UTF-8 で保存し直すと現場で文字化けします。

`.bat` には順序の決まりもあります。`chcp 932` より前に非ASCIIのバイトがあると、
その部分は違うコードページで解釈されます。CP932 の2バイト目には `0x5C`(`\`)や `0x40`(`@`)が
現れるため、コメントの文字が区切り記号に化けて構文が壊れます。
`tests/test_launch_files.py` が文字コード・改行・この順序を見ています。
