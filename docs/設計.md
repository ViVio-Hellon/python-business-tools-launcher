# 設計 — 業務ツール統合ランチャー

要件定義書(`business-tools-launcher` 要件)と汎用Webアプリ作成 基盤仕様書に対して、
**何をどう決めたか**と、**なぜそう決めたか**を書きます。

---

## 1. このランチャーの立ち位置

ランチャーは業務ロジックを持ちません。持つのは順序と状態だけです。

```
Windows
   │
   ▼
business-tools-launcher (常駐・tkinter)
   │  ボタンを押す
   ▼
各リポジトリの start.bat を実行
   │
   ▼
GET /api/health が応答するまで待つ   ← ここを飛ばさない
   │
   ▼
ブラウザーを開く
```

各ツールの Python の起こし方は、それぞれのリポジトリの `start.bat` に集約したままにします
(要件定義書 §12.2 / §21)。ランチャーが知っているのは「BATを呼ぶ」ことと「`/api/health` を見る」ことだけです。

### 監視レベル

基盤仕様書 §3 の3段階のうち、**レベル1(通常の操作アプリ)** を選びました。

ランチャー自身は長時間処理も自動実行も持たず、ボタンを受けて起動・停止するだけだからです。
ただし、**起動する相手はレベル2以上**(看板と総合ツールは長時間処理を持つ)なので、
停止のときだけ相手の事情を汲みます — 実行中の処理があれば止めずに知らせ、中断してよいかは利用者が決めます(基盤仕様書 2.8)。

---

## 2. 起動完了の判定

`start.bat` を実行しただけでは起動完了と判断しません(要件定義書 §21)。

判定に使うのは相手の `GET /api/health` です。4つのツールはどれも同じ起動基盤を使っていて、
次の形で応答します。

```json
{
  "app_id": "nlm.nippou-tool",
  "display_name": "日報管理ツール",
  "version": "3.0.0",
  "app_root": "C:\\業務ツール\\日報",
  "port": 8733,
  "pid": 12345,
  "ready": true,
  "stage": "アプリを準備中"
}
```

**`app_id` の一致まで見ます。** HTTPが返るだけでは足りません — 同じポートを別のアプリが
使っていることがあるからです(基盤仕様書 2.3)。`ready` が false のあいだは待ち続け、
`stage` をランチャーバーに出して「進んでいる」ことを見せます(基盤仕様書 2.2)。

> 要件定義書 §7.2 の例は `GET /health` ですが、4リポジトリの実装は `/api/health` です。
> どちらでも動くよう、**確認URLを設定にしました**(`port` + `health_path`、必要なら
> `health_url_override` で丸ごと差し替え)。相手側を書き換えずに済みます。

### PIDとポートは応答から取る

ランチャーが `subprocess` で起こしたのは `cmd.exe` であって、業務ツール本体ではありません。
そのPIDで止めようとしても本体は落ちません。**止めるときに使うPIDは `/api/health` が返した値**です
(要件定義書 §10)。

`start.bat` を起こしたプロセスのPIDも別枠(`launch_pid`)で記録します。
本体が応答しないときの後片付けに使います。

## 3. 安全な停止

要件定義書 §21 が禁じているのは1点、**Pythonプロセス名だけを指定して一括終了しない**ことです。

穏やかな方法から順に試します。

| 順 | 方法 | いつ使うか |
|---|---|---|
| 1 | 相手の `stop.bat` に任せる | いちばん確実。相手の作法で止まる |
| 2 | `POST /api/shutdown` | `stop.bat` が見つからないとき |
| 3 | 記録したPIDで止める | 応答しないときだけ |

`stop.bat` は設定しなくても、**`start.bat` の隣**を既定として拾います。
4つのツールはどれも `start.bat` と `stop.bat` が並んでいるので、設定項目を1つ減らせます。

### PIDで止める前の照合

PIDは使い回されます。記録した時点では日報だったPIDが、止めるころには無関係なプロセスに
なっていることがあります。そこで落とす前に、**そのプロセスのコマンドラインにツールの置き場所が
入っているか**を確かめます。

- 取れないときは **止めません**。誤って別のアプリを落とすより、止まらないほうが害が小さいからです。
  止まらなければ利用者は気づいて手で対処できますが、他人の処理を落とすと気づかれないままデータが失われます。
- 印が短すぎる(`C:\` など)ときも照合しません。どのプロセスにも一致してしまい、照合が形だけになるためです。
- コマンドラインの取得は `wmic` → PowerShell (CIM) の順です。`wmic` は新しい Windows では既定で
  入っていないため、そこだけで諦めると「照合できない=止めない」でツールを終了できなくなります。

### 引き取り待ち(ゾンビ)の扱い

ランチャーは `start.bat` を**自分の子として**起こします。POSIX では、終了した子は親が引き取るまで
PID表に残ります。これを「生きている」と答えると、止まったものを止まっていないと報告し続けます。
`_is_alive()` は `/proc` を見て、引き取り待ちの状態を「終了済み」と答えます。

止めたあとに `cmd.exe` が残った場合は落とします。残すと、見えないコンソールが切り替えのたびに1つずつ増えます。

## 4. 切り替え

```
現在：日報
   ↓  [看板] を押す
日報を終了しています...        ← STOPPING
   ↓  /api/health が応答しなくなるまで待つ
看板を起動しています...        ← STARTING
   ↓  /api/health が app_id 付きで応答するまで待つ
現在：看板                     ← RUNNING
```

順序は `app_manager.ToolManager` が持ちます。要求ごとに番号を振り、**新しい要求が来たら古い待機を
打ち切ります** — 日報の起動を待っている最中に看板を押されたとき、2つの待機が同時に画面を書き換えないためです。

同じツールのボタンをもう一度押したときは起動し直さず、ブラウザーだけを開きます(要件定義書 §9)。

### ランチャー外で動いているツールの引き継ぎ

ランチャーを再起動したときや、利用者が `Start.vbs` から直接ツールを起動していたときは、
「動いているのにランチャーは何も知らない」状態になります。そのままボタンを押すと二重起動です。

起動時に `adopt_running()` が、記録と、設定されている全ツールの `/api/health` を当たって、
動いているものを現在のツールとして引き継ぎます。

## 4.5 ブラウザー画面 (要件定義書 §8.3)

切り替えのときに、そのツールを映している画面だけを閉じる。利用者が別に開いている
Google やメールのタブは閉じない。

### なぜ `webbrowser.open()` を使わないか

`webbrowser.open(url)` は既定のブラウザーへURLを渡すだけで、**開いたタブへの手がかりを
何も返さない**。あとからそのタブだけを閉じる方法が無い。かといって `chrome.exe` の
プロセスを落とすと、Google もメールも道連れになる — §8.3.3 がいちばん避けたい状態そのもの。

### 専用プロファイルのアプリウィンドウ

```
chrome.exe --app=http://127.0.0.1:8733/
           --user-data-dir=%LOCALAPPDATA%\BusinessToolsLauncher\browser\nlm.nippou-tool
           --no-first-run --no-default-browser-check
           --disable-session-crashed-bubble
```

こうすると3つが同時に手に入る。

1. **ランチャー自身の子プロセスになる** → PIDで閉じられる
2. **利用者のふだんのブラウザーとは別インスタンス** — プロファイルが違うので
   ウィンドウもプロセスも共有しない → 落としても通常のタブに手が届かない
3. **タブもアドレスバーも無い1画面** → 業務ツール専用の窓になる

「関係ないタブを閉じない」ことを、後から見分けるのではなく**構造上あり得なくする**のが要点。
その上でさらに、閉じる前にコマンドラインへ専用プロファイルの道が入っていることを照合する
(バックエンドを止めるときと同じ守り方)。

プロファイルは**ツールごとに分ける**。前の窓が閉じきる前に次を起こしたとき、同じプロファイルを
掴み合って新しい窓が既存プロセスに合流し、こちらの手がかりが消えることを避けるため。

探す順は Edge → Chrome → Chromium。Edge はWindowsに必ず入っているので先頭に置いた。
`config/launcher.json` の `browser.preferred` で変えられ、見つけられない置き方をしている端末には
`browser.extra_paths` で実行ファイルを直接指定できる。

### 見つからなかったとき

Chromium系が1つも無い端末では `webbrowser.open()` に落とす。**その場合は閉じられない**ので、
記録に `browser_pid = 0` が残り、画面には「切り替えのときに自動では閉じないので、
不要になったタブは手で閉じてください」と出す。黙って閉じたことにしない。
`start_debug.bat --check` がどちらになるかを表示する。

### 処理順序 (§8.3.2)

```
現在：日報
   ↓ ［看板］を押す
日報の専用ブラウザー画面を閉じる      ← ここが先
   ↓
日報のバックエンドを停止
   ↓
日報の終了を確認
   ↓
看板を起動 → 起動完了を確認
   ↓
看板の専用ブラウザー画面を開く
   ↓
現在：看板
```

画面を先に閉じるのは、逆にすると閉じるまでのあいだ利用者の画面に「接続できません」が
出るため。

### 画面とバックエンドを別々に持つ (§8.3.4)

`Status` は `responding`（バックエンド）と `browser_open`（画面）を別の値として持つ。

**ただし「画面だけ閉じた状態」は長くは続かない。** 各業務ツールは
「誰も見ていなければ終了する」見張り (`idle_exit`) を持っていて、画面が送る心拍
(`POST /api/alive`) が途切れると数秒で自分から落ちる。タブを閉じると `sendBeacon` で
即座に伝わり、猶予は 8 秒。

ツール側の設計は正しい — 窓がブラウザーのタブしか無い前提なら、タブを閉じたら終わるのが自然。
**ランチャーという「もう1つの窓」が増えたことで前提が変わった**だけ。

ここで取れる道は3つある。

| 案 | 内容 | 代償 |
|---|---|---|
| A | 実態に合わせて「まもなく終了します」と出す | 画面だけ開き直せる時間が短い |
| B | ランチャーが代理で心拍を送って生かし続ける | 誰も見ていないのに動き続ける |
| C | 設定で選ばせる | 実装が増える |

**A を採った。** B はツール側の判断を黙って上書きすることになり、長時間処理を持つツール
（看板・総合ツール）では「誰も見ていないのに動き続ける」状態を作る。

バーは `現在：日報（画面を閉じました・まもなく終了します）` と出し、詳細に
「実行中の処理があれば終わるまで待ちます／続けて使うときはもう一度ボタンを押してください」
を添える。もう一度押したときは、まだ生きていれば画面だけ開き直し、すでに落ちていれば起動し直す。

`stop.bat` は別プロセスなので、画面のPIDとプロファイルの道も `runtime/current.json` に
書いておく。そうしないとコンソールから画面を閉じられない。

## 5. 設定 (要件定義書 §13 / §14)

端末ごとにリポジトリの置き場所が違うので、`start.bat` のパスはコードに埋め込みません。

```
config/launcher.json   製品の既定値
distribution/          配布先フォルダ (あれば読む)
        ↓ 起動時。**その端末にまだ無いものだけ**入れる
%LOCALAPPDATA%\BusinessToolsLauncher\data\launcher.db   ← 動作中の唯一の参照先。既存データが優先
        ↑ 設定画面 (管理者パスワード)
```

**既定値に `start.bat` のパスは入れません。** もっともらしいパスを入れると、
「設定したつもりで別の場所を指している」状態を作るためです。空にしておけば設定画面が「未設定」と出します。

管理する項目(要件定義書 §14)と、その持ち方:

| 項目 | 列 | 備考 |
|---|---|---|
| アプリID | `app_id` | 主キー。`/api/health` の照合に使う |
| 表示名 | `display_name` | ボタンの文字 |
| start.batのパス | `start_command` | 設定画面の主役 |
| 作業ディレクトリ | `work_dir` | 空なら `start.bat` の置き場所 |
| 使用ポート | `port` | |
| 起動確認URL | `health_path` / `health_url_override` | ふだんは `port` + `health_path` から組み立てる |
| 停止方法 | `stop_method` | `auto` / `stop_bat` / `shutdown_api` / `pid` |
| 起動引数 | `start_args` | 既定 `--no-browser` |

起動確認URLを2つの列で持っているのは、**出どころを1つに保つ**ためです。
`port` と完成形URLを対等に持つと、ポートを直したのにURLが古いまま、という食い違いが起きます。
ふだんは `port` から組み立て、どうしても違う形が要るときだけ `health_url_override` で差し替えます。

### 配布する前に起動ファイルを決めておく

**設定はランチャーのフォルダーと一緒に移動しない。** 各PCの `%LOCALAPPDATA%` にあるので、
設定済みのフォルダーをコピーしても、配った先では全ツールが「未設定」から始まる。

以前は「既定値に起動ファイルのパスを入れない」としていた。もっともらしいパスを入れると、
設定したつもりで別の場所を指したまま気づかない、という理由だった。これは**ランチャーの作り手が
パスを推測して入れる**場合の話で、**配置を知っている配布者が書く**場合には当たらない。
そこで `config/launcher.json` の `tools` に `start_command` を書けるようにした。

| 決めごと | 理由 |
|---|---|
| ランチャーのフォルダーを起点にした**相対パス**を許す | 配った先の置き場所 (`C:\業務ツール\` / `D:\Tools\`) が違っても同じ書き方で指せる |
| 設定画面の入力は絶対パスのまま | 起点が決まっているのは配布先フォルダと既定値だけ。画面の入力は起動した場所で指す先が変わる |
| **実在するときだけ**埋める | 実在しないパスを入れると空欄が「間違った値」に変わり、あとでツールを置いても埋め直せない |
| **空欄だけ**埋める | 利用者が設定画面で入れた値は、その端末の正しい値。上書きしない |
| 起動のたびに見る | あとからツールを置いた端末でも、次の起動で空欄が埋まる |

`start_debug.bat --check` は、配布先フォルダにあるのに埋まっていないツールについて、想定していた
パスと解決先を出す。配った先で「なぜ未設定か」がその場で分かる。

### 配布先フォルダ (`distribution/`)

最初は `config/launcher.json` の `start_command` を配布の手段にしていた。これには2つ弱みがある。

- **ランチャーを新しい版に入れ替えると消える。** `launcher.json` は製品の既定値で、版と一緒に入れ替わる
- **手で書くしかない。** JSON の罠 (コメント不可、`\` の重ね書き) を配る人が毎回踏みうる

そこで現場のものをランチャーのフォルダーの中の `distribution/` にまとめた。

```
distribution/
├─ settings.json   ツールの設定 (起動ファイルはランチャー起点の相対パス、/ 区切り)
├─ password.json   管理者パスワードの照合値
└─ README.txt      このフォルダーの説明 (BOM 付き UTF-8・CRLF。メモ帳で読める)
```

**その端末にすでにあるデータが優先。** 起動時に配布先フォルダがあれば読むが、入れるのは
その端末に**まだ無いもの**だけ。

| 決めごと | 理由 |
|---|---|
| 配布先フォルダがあれば、**その一覧が正** (製品の既定値を混ぜない) | 混ぜると、配布元で消したツールが配った先に「未設定」で出てくる |
| すでにあるツールの値には触らない | その端末で直した値 (起動ファイル・表示名・ポート) を、配り直しで消さない |
| ただし**工場出荷のままの行**は配布先フォルダにそろえ、無ければ外す (`_untouched_default_rows`) | 起動ファイルが空で、［設定］で変えられる項目が既定値のままなら、人は何も入れていない。配布先フォルダを置く前に一度起動しただけの端末も、きれいに引き継げる |
| まだ無いツールは入れる (`seeded_tools` に無いもの) | 無いものは「まだデータが無い」。5個目を足して配れば、使っている端末にも届く |
| 空欄の起動ファイルは埋める | 空欄も「まだデータが無い」。あとからツールを置いた端末でも次の起動で埋まる |
| その端末で消したツールは戻さない | `seeded_tools` に記録が残る。消したのに復活すると、消したことにならない |
| そろえたい端末では**明示的に**置き換える (`reload_from_distribution`) | 既定の動きは「既存優先」のまま、例外だけを利用者の操作に任せる。置き換える前に控えを取る |
| **画面から作る** (`export_tools`) | 手で書かせない |
| 相対パスは**実体の場所どうし**で求める (`os.path.realpath`) | ランチャーの場所は `Path.resolve()` で実体になる。ネットワークドライブ (Z:) やジャンクション越しに選んだ起動ファイルを、別のドライブと取り違えない |
| 同じアプリIDが2度あれば1つにまとめる | 手で直したときの取りこぼしで、同じツールが2度入らないように |
| 作る前に画面の内容を保存する | 画面と作った中身をずらさない (「直したのに届かない」を作らない) |
| 端末ごとに違ってよい項目は書かない | 作業フォルダーの上書き・起動確認URLの差し替え・PCのモード・バーの位置 |
| 入れるのは**書かれている項目だけ**、形の合わない値は飛ばす | ポートに文字、などの1項目の誤りで、起動が止まったりツールの設定が壊れたりしない |
| 起動ファイルは**実在するときだけ**入れる | 実在しないパスを入れると空欄が「間違った値」に変わり、あとで置いても埋め直せない |
| 書き込みは別名に書いてから差し替える。断られたら少し待って試し直す | 途中で落ちても壊れた JSON を配らない。共有フォルダーでは、ほかの端末が読んでいる一瞬だけ Windows が差し替えを断る |
| 設定とパスワードは別のファイル | 作り直しても鍵が変わらない。忘れたら鍵のファイルだけ消せる。壊れた設定を作り直すために［設定］を開ける |

`launcher.json` の `start_command` も読む (以前の版で書いた人のため)。同じアプリIDなら、
配布先フォルダの項目が勝つ。

### 管理者パスワード

［設定］を開く前に尋ねる。**ライン作業者が起動ファイルをうっかり変えてしまうのを防ぐ**ための鍵。

- パスワードは配布先フォルダに置く → 配ると全端末で共通になる。端末ごとの設定DBに置くと、端末の数だけ決める手間が出る
- 保存するのは照合用の値だけ (`hashlib.pbkdf2_hmac` SHA-256、20万回、16バイトの塩)。比べるのは `hmac.compare_digest`
- まだ無ければ**その場で決めてもらう**。決めなければ開かない。保存できなければ「決めた」とは言わない
- `password.json` が壊れていれば開かない (確かめようがない)。起動は止めない

**守りの固い鍵ではない。** フォルダーに書き込める人は `password.json` を消せば外せる。
それが忘れたときの戻し方でもある。ツールの設定 (`settings.json` と各端末の設定DB) は失われない。

尋ねる順番と回数は `admin_lock` に置き、tkinter は `ui/password.py` の入力欄だけにした。
画面の無い環境でも流れを試験できる。

### 古い設定DBを新しい版で開く

`CREATE TABLE IF NOT EXISTS` は、表がすでにあれば何もしない。新しい版で列を増やすと、
古い設定DBを持つ端末では読んだとたんに落ちる。起動時に `_SCHEMA` を正として、
**無い列だけ既定値つきで足す** (`_add_missing_columns`)。

### 配布で壊れやすいところ

- **JSON はコメントを許さない。** README の例に `//` を書いていたため、写すと設定が壊れる状態に
  なっていた。壊れると `app_config` は既定値に落ち、既定値のツール一覧は空なので、**新しい端末では
  ボタンが1つも出ない**。README の例を正しい JSON に直し、`test_launch_files` で README 内の
  JSON をすべて読めることを固定した。起動時にも設定の読み込みに失敗したらダイアログで知らせる。
- **JSON では `\` を2つ重ねる。** `"..\日報\start.bat"` と1つで書くと `Invalid \escape` で壊れる。
  区切りは `/` を推奨する（Windows でもそのまま通る）。

### ツールを増やす道は2つ (要件定義書 §14)

起動・切替・停止のコードは**ツールの数を一切知らない**。ボタンは `all_tools()` の
行数ぶん作られ、状態機械は「いま選ばれている1つ」しか持たない。だから増やすのは行を足すだけで、
ランチャー本体の書き換えは要らない。

| 道 | 誰が | 届く範囲 |
|---|---|---|
| 設定画面の［＋ ツールを追加］ | 端末の利用者 | その端末だけ |
| 1台で足して**配布先フォルダを作り直す** | 配布する側 | 配る全端末 (まだ無いツールとして入る) |

**既定値からの投入は「まだ投入していないアプリIDだけ」。** 全体で1つの「投入済み」印にすると、
あとから書き足しても、すでに使っている端末には永久に入らない。逆に印が無いと、利用者が
消したツールが次の起動で復活する。そこで `seeded_tools` にアプリIDごとの記録を持つ。

- 既存の行には触らない → 利用者が入れた `start.bat` のパスが残る
- 消したツールは記録が残るので復活しない

**①ではアプリIDを手で写させない。** `start.bat` の隣の `config/app.json` から読み取る ──
1文字違うだけで起動確認が永久に通らず、しかも画面には「応答がありません」としか出ないので
原因にたどり着きにくい。役割 (現場/資材、看板/倉庫/閲覧) を持つツールは最初の役割のポートを
既定にし、あとから設定画面で直せるようにしてある。

既存の行のアプリIDは変更できない。`/api/health` の照合と実行中の記録がこの値で結びついて
いるので、途中で変えると動いているツールを見失う。

使わないツールは `enabled` を落とせば、消さずに隠せる。

### 数が増えたときバーに収める

バーは**折り返さないし、窓も広がらない**（`resizable(False, False)`、幅は画面幅で頭打ち）。
そのまま増やすと、入りきらないボタンが**黙って切れて押せなくなる** — エラーも警告も出ないので、
利用者はそのツールが使えないことに気づけない。

そこで入りきらないぶんを［▼］のメニューへ回す。要件 §5.2「業務ツールの操作をできるだけ
邪魔しない」を守ったまま、数が増えても破綻しない。

| 決めごと | 理由 |
|---|---|
| 並び順は変えない | 設定の `order_no` が並びの根拠。ここで入れ替えると設定と食い違う |
| **使用中のツールは必ず出す** | ［▼］に隠れると、どれが動いているか見えなくなる |
| ［▼］の幅を先に取り置く | 取り置かないと、［▼］を出した拍子にまた1つ切れる |

判定は `launcher/ui/geometry.py` の `fit_buttons()` に置いた。**画面まわりで実機でしか
気づけない部分**なので、tkinter に触らない純粋な計算にして試験で固定してある
（予算に収まること、並び順、使用中が必ず入ること、予算0や1つも入らない場合）。

バー側がやるのは測ることだけ ── 全部出して `winfo_reqwidth()` を読み、ツール以外が使う幅を
引いた残りを予算として渡す。

### PCごとのモード (要件定義書 §15)

`pc_settings` テーブルに保存し、設定画面から変更できます。利用者に毎回選ばせません。

**初回起動時の選択ダイアログは作っていません。** §15 は将来要件で、
「詳細なモード内容は各業務ツール側の要件として別途定義する」とあります。
選択肢が決まっていない段階で全端末に選択を強いると、意味のない値が保存されるだけになります。
モードの中身が決まったら、保存と設定画面はそのまま使えます。

## 6. 層の分け方 (基盤仕様書 2.5)

```
Start.vbs / start_debug.bat / stop.bat     利用者の入口
        │
launcher.py            環境確認 → 多重起動判定 → 画面を出す
        │
launcher/ui/           tkinter。**ここだけが画面を知る**
        │
app_manager.py         起動・切り替え・停止の順序と状態
        │
process_manager.py     対象の確認と安全な停止
launcher/health.py     起動確認
launcher/tool_registry.py   設定 (SQLite)
```

画面より下の層は tkinter を読み込みません。`stop.bat` からの停止、CIでの試験、
tkinter の入っていない端末のいずれでも動かせるようにするためです。
`tests/test_no_tkinter.py` が構文木を見てこれを固定しています。

`launcher.py` だけは例外で、起動前の確認と失敗の通知にダイアログを使います。
`Start.vbs` はコンソールを出さないので、そこで伝えないと「何も起きない」ようにしか見えません。

### 起動ファイルは `.bat` と `.vbs` のどちらでもよい

`start.bat` を推奨する。引数が届き、出力ログと戻り値も取れる。`start.bat` は各ツールの
診断用入口だが、ランチャーから呼ぶときはコンソールが出ない（`CREATE_NO_WINDOW` で隠し、
末尾の `pause` は標準入力を `DEVNULL` にして素通りさせる）。実質「引数を転送してくれる入口」
として使っている。

`.vbs` も指定できるが、**引数を転送するとは限らない**。4ツールの `Start.vbs` は
`pythonw "<script>"` を決め打ちで実行しており、転送する処理が無い（`WScript.Arguments` の
参照が0件）。

そこで**中身を読んで判定する** (`Tool.forwards_args`)。`WScript.Arguments` があれば転送する、
無ければしない。読めなければ「転送しない」に倒す ── **届くと思い込んで2枚開くより、
届かない前提で1枚に寄せるほうが害が小さい。**

届かないと `--no-browser` が効かず、ツールは自分でブラウザーを開く。そこへランチャーも
専用ウィンドウを開けば**同じツールの画面が2枚**になり、作業状態を奪い合う。そこで
`Tool.suppresses_browser` が偽のときは**ランチャーは画面を開かない**。

この判定は `.bat` にも効く。`--no-browser` を外した `.bat` でも、ツールが自分で開くので
ランチャーは開かない。以前は両方開いて2枚になっていた。

`.vbs` の実行には `wscript.exe` を挟む。`Popen` が使う `CreateProcess` は**ファイルの
関連付けを解決しない**ので、`.vbs` を直接渡しても動かない（エクスプローラのダブルクリックとは
仕組みが違う）。

## 5.5 多重起動の防止 (要件定義書 §9 / 基盤仕様書 2.4)

**素早く2回押されたときに耐えられるか**が勝負どころ。`Start.vbs` は pythonw で起動するので
押しても数秒は何も出ない。ツールの起動にも時間がかかる。どちらも「反応が無いからもう一度押す」が
現実に起きる操作で、そこが守れていなければ防止は名ばかりになる。

### ランチャー自身 — 調べてから書かない

「調べる」と「書く」を分けると、その隙間に割り込める。

```
A: ロックを調べる → 無い
B: ロックを調べる → 無い     ← ここが隙間
A: ロックを書く
B: ロックを書く
→ 両方が起動する
```

そこで**作成と占有を1回の操作で行う**。`os.open(..., O_CREAT | O_EXCL)` は
「無ければ作る、あれば失敗する」を割り込みなしで行うので、同時に来ても必ず片方だけが成功する。

`check_existing()` は診断のために残してあるが、起動の判断には使わない。

### 書き込み途中のロックを「壊れている」と誤らない

場所を押さえてから中身を書くので、そのあいだロックは**空のファイル**として見える。
これを壊れた扱いで片付けると、**押さえたはずのロックが消えて、もう1つが起動できてしまう**
（実際にそうなっていた）。書き手はすぐ終わるので、`_read_lock_settled()` が最大1秒だけ待って
読み直す。それでも読めなければ本当に壊れているので片付ける。

### 業務ツール — 起こしている最中の印を持つ

ボタンを2回押すと、どちらの要求も「まだ何も動いていない」と見て、両方が `start.bat` を実行して
いた。2つ目はポートが空いていないので必ず失敗し、**起動できているのに「起動できませんでした」**
と出ることになる。

`_starting` に「いま起こしているツール」を持ち、`_spawn` の直前で見る。この確認と `_spawn` は
同じロックの中で行う（確認と実行が離れていては意味がない）。待ち時間の長い `wait_ready` は
ロックの外に置く。

### 画面を2枚にしない — プロセスの二重起動とは別の話

**プロセスが1つでも、画面が2枚あればどちらにも入力できる。** 業務ツールの作業状態は
プロセスに1つしか無い（総合ツールの `selection_session` は `_session` をモジュール直下に持ち、
docstring にも「画面が覚えていたことをプロセス側に置く」とある）。2枚あれば奪い合う。

ランチャーだけで操作する限り、画面は常に1枚になる。

| 操作 | 画面 |
|---|---|
| ツールを選ぶ | 1枚開く |
| 別のツールへ切り替える | 前の画面を閉じてから次を開く |
| 同じツールをもう一度押す | 開いていれば**開き直さない** |

ただし1か所だけ穴があった。**画面の手がかり（`browser_pid`）を失うと、
「画面が無い」と判断してもう1枚開いていた。** 手がかりは
`runtime/current.json` にあるが、ランチャー外で起動していた場合や、生存監視が誤って記録を
消した場合には失われる。

そこで**開く前に、すでに開いている画面を探す**。専用プロファイルの道はそのツールの画面だけが
持つので、それを印にプロセスを探せば見つかる。見つけた画面の手がかりを取り戻すので、
そのあとの切り替えでもきちんと閉じられる。

Windows ではプロセス一覧を1回の呼び出しでまとめて取る。1つずつ問い合わせるとプロセスの数だけ
外部コマンドを起こすことになるが、探すのは画面を開く前の1回だけなので、まとめて取って絞る。

### 照合の手段が無い端末でも、自分で開いた画面は閉じる

「このプロセスは本当に自分のものか」の照合は、すべて外部コマンド (`wmic` / PowerShell) で
コマンドラインを取ることに頼っていた。**両方使えない端末がある** ── `wmic` は Windows 11 24H2
以降は既定で入っておらず、工場の端末では PowerShell を一般利用者に禁じていることがある。

そうした端末では照合がすべて「確かめられない→触らない」に倒れ、**切り替えのとき画面を
閉じられずに2枚になっていた。** 設計どおり安全側に倒れた結果だが、いちばんよく通る道が
壊れていた。

ランチャーが自分で開いた画面なら、**開いたときのプロセスの手がかり (Popen) を持っている。**
これは外からコマンドラインを照合するより確かな証拠で、手がかりを持っているあいだ OS はその PID を
他へ回さないので、使い回しも起きない。`browser.is_spawned()` が真なら照合を省いて閉じる。

外から調べるしかない道 (前回のランチャーが開いた画面、記録を失ったときの探し直し、PID での停止)
は、この端末では引き続き使えない。**試験でも「できないこと」として固定した** (`LockedDownPcTests`)。
できないことを試験が「できる」と言うと、現場で初めて気づくことになる。

`start_debug.bat --check` に「プロセスの照合」を出すので、配る前に分かる。

### ランチャーの外から開かれた画面

`http://127.0.0.1:8733/` をブラウザーに直接打つ、ツールの `Start.vbs` を直接実行する ──
これらは**ランチャーを使わない操作**で、ランチャーには防ぎようがない（127.0.0.1 で待ち受ける
Webアプリである以上、URLを知っていれば何枚でも開ける）。

運用の決めごととして「ツールはランチャーからだけ起動する」で足りる。コードで塞ぐなら
ツール側で画面を数える必要があり、4つのリポジトリすべてに手が入る。

### 打ち切ったツールを置き去りにしない

起動を待っているあいだに別のツールが選ばれると、こちらは記録を持たないまま去る。すると
**止める人が誰も居なくなる**。`_abandon()` が、立ち上がっていれば止めてから抜ける。

## 6.5 バーの置き場所 (要件定義書 §5.1 / §5.2)

置き場所は状態で決まる。

| 状態 | 置き場所 | 理由 |
|---|---|---|
| 何も選んでいない | `center`（画面中央） | **ランチャーが主役**。起動直後に探さずに見つかる |
| ツールを選んだ / 動いている | `bottom_left`（左下） | **業務画面が主役**。隅へ寄って邪魔をしない |

移動は 0.18 秒かけて滑らせる。瞬間移動だと、常駐しているものが突然別の場所に現れたように
見えて不具合と区別がつかない。`move_animation_ms` を 0 にすれば瞬間移動になる。

計算だけを `launcher/ui/geometry.py` に切り出してある。**画面まわりで唯一、間違えると
実機でしか気づけない部分**なので、tkinter に触らない形にして試験で固定した。

### 手で置いた位置がいちばん強い

自動の移動と「動かした位置を覚える」は、放っておくと互いに喧嘩する — 利用者が置いた場所へ
自動移動が上書きし、動かすたびに戻される。そこで**手で動かしたら自動移動をやめる**。

判定は単純にした。`pc_settings` に位置が入っていれば手動、無ければ自動。値の有無そのものが
印なので、「手動フラグ」を別に持たない。自動へ戻すのは設定画面の［自動に戻す］で、
中身は `clear_pc_setting()` の1行。

### 自分で動かしたぶんを「利用者が動かした」と取り違えない

`geometry()` を呼ぶと `<Configure>` が飛ぶ。区別しないと、**自動で寄せた位置を利用者の
操作と誤認して手動モードに落ち、以後の自動移動が止まる**。自分で動かすあいだは印を立て、
`<Configure>` を無視する。通知は少し遅れて届くので、余韻 (250ms) をもって戻す。

### 幅は「全部出ている状態」で測る

「ツール停止」と「詳細」はふだん畳んでいるが、**畳んだ幅で窓を決めてはいけない**。
窓は `resizable(False, False)` で広がらないので、あとで出てきたぶんが右端で切れる。
ツールが動き出すたびに起きる。`_content_width()` は測るあいだだけ全部を出す。

同じ理由で、設定画面で5個目のツールを足したあとは幅を取り直す。ただし**位置は動かさない** ──
利用者が置いた場所から勝手に飛ぶと、探し直すことになる。

### 覚えた位置が画面の外なら捨てる

二画面を外した、解像度を変えた、といったときに覚えた座標をそのまま使うと、
**バーが見えない場所に出たまま戻せなくなる**。掴める程度に見えているかを確かめ、
見えていなければ既定の位置に戻す。端に少し寄せた程度は、利用者が意図したものとして残す。

## 6.6 バージョン表示

現場でいちばん困るのは「入れ替えたはずなのに直っていない」状態。原因はたいてい次のどちらかで、
**見分けがつかないと端末まで見に行くことになる**。

- 入れ替えたつもりで、別のフォルダーを起動していた
- 入れ替えたが、古いプロセスが動いたままだった

そこで**2つの版を並べて出す**。

| 表示 | 出どころ | 分かること |
|---|---|---|
| 入っている版 | そのツールの `config/app.json` | いま置かれている版。**停止中でも分かる** |
| 動いている版 | `GET /api/health` の `version` | いま動いているプロセスの版 |

食い違えば「版ちがい」。古いプロセスが残っている合図なので、直し方 (`stop.bat` で止めてから
起動し直す) まで添える。場所は**動いているほうを優先して出す** — 設定と違うフォルダーが
動いていることがあり、それ自体が答えになるため。

### ランチャー自身の版はソースに置く

出どころは `launcher/__init__.py` の `__version__` ただ1つ。`config/launcher.json` には置かない。

アプリID・表示名・ポートは端末ごとに変わりうるので設定に置くが、**版はコードと一体のもの**で、
フォルダーごとコピーして配る運用でも必ずソースと一緒に動く。設定から変えられると、表示された版が
嘘になりうる。

さらに実務上の理由がある。設定ファイルは壊れることがあり、そのとき `app_config` は既定値に落ちる。
版まで設定から読んでいると `0.0.0` と表示され、**いちばん版を知りたい場面（壊れた端末の調査）で
答えが出ない**。ソースから読めば、設定が読めなくても版は分かる。

### 出口は4つ、中身は1つ (`launcher/version_info.py`)

- ウィンドウのタイトル → タスクバーと Alt+Tab に出る。**画面を見ていなくても窓の一覧から分かる**
- バーの版バッジ → バージョン情報ダイアログ（ボタンを増やさず、バッジ自体を入口にする）
- `start_debug.bat --check` → 同じ内容をコンソールへ
- 起動ログ → 起動のたびに「どの版が動き出したか」を1行残す

`version_info` は tkinter に触らない。画面とコンソールが同じ中身を使うためで、
`describe()` は全角を2桁と数えて桁を揃える (`len()` のままだと「日報」と「カレンダー」が
揃わない)。

コンソールのログは INFO 以上にした。診断起動は利用者が読むものなので、起動確認の応答なしを
1件ずつ出す DEBUG が混ざると、肝心のバージョンや設定の行が埋もれる。細かい記録はファイルに残る。

## 6.7 開いたままにしたときに効いてくること

長く開いたままにする運用で、放っておくと効いてくるものをここにまとめる。

### 応答が1回途切れただけで「終了した」と断じない

起動確認のタイムアウトは 1.5 秒しかない。スリープからの復帰直後、監視レベル2のツールが
重い処理をしているあいだ、一時的な負荷 — どれでも 1 回は落とす。

1 回で断じると、**動いているツールを落ちた扱いにして記録まで消す**。記録が消えると
`stop.bat` からも止められなくなる。そこで `health_failures_before_dead`（既定 3）回
続けて応答が無いときだけ終了と判断し、途中で戻れば数え直す。5 秒間隔なので約 15 秒で気づく。

### ツールの出力ログは日数だけでは守れない

`launcher_*.log` は日付で分かれるので `KEEP_DAYS` で消せる。`tool_<アプリID>.out.log` は
**日付で分かれず、動いているあいだ追記され続ける**ので、日数では 1 つのファイルが育つのを
止められない。開くときに大きさを見て、`tool_log_max_mb`（既定 5MB）を超えていれば
`.1` `.2` と退ける（`tool_log_keep`、既定 2 世代）。

書いているのは `logging` ではなく**子プロセス自身**なので、`RotatingFileHandler` は使えない。
こちらにできるのは「開く前に退ける」だけ。

### 使われなくなった画面プロファイル

`browser/<アプリID>/` は Chromium のプロファイルで、使うほど膨らむ。設定からツールを消しても
残り続けると、誰も使わないキャッシュが端末に溜まる。起動時に**登録の無いものだけ**消す
（使っているツールのぶんは残す — 消すと次に開くときに作り直しになる）。

### 引き継いだツールの画面は閉じられない

ランチャーを再起動して記録が失われた場合や、利用者が `Start.vbs` から直接ツールを起動していた
場合、`adopt_running()` は `/api/health` からしか情報を得られないので `browser_pid` が入らない。
切り替えのときに画面を閉じられないので、**引き継いだ時点でそう伝える** — 黙っていると
「閉じたはずの画面が残っている」と見える。

## 7. 現場で踏みやすいところ

### 自分自身への通信にプロキシを通さない

`urllib` の既定は環境変数や Windows のインターネット設定からプロキシを拾います。
社内PCではたいていプロキシが入っており、除外一覧に `127.0.0.1` が無いと
**自分自身への通信までプロキシへ送られて失敗します**。相手ツールは待ち受けているのに
応答が返らず、時間切れで「起動できませんでした」になります。

`launcher/health.py` の送信口は `ProxyHandler({})` を明示的に挟んでプロキシを外しています。
起動に失敗したときは、いま効いているプロキシ設定も画面に出します。

### BAT末尾の `pause` で固まらせない

診断用のBATは末尾に `pause` を置くことがあります。ランチャーから呼ぶとコンソールが見えないので、
そのままでは永久に待ち続けます。子プロセスの標準入力を `DEVNULL` にすると、`pause` はすぐ抜けます。

### ツールの出力はファイルへ逃がす

`subprocess.PIPE` で受けてはいけません。業務ツールはランチャーが生きているあいだ動き続けるので、
誰も読まないパイプはやがて詰まり、ツールごと固まります。
`logs/tool_<アプリID>.out.log` へ追記すれば詰まらず、調査の材料にもなります。

### 起動できないときに何を出すか

時間切れの一言だけでは、次に何を見ればよいか分かりません。場合分けして出します。

| 状況 | 出すもの |
|---|---|
| `start.bat` が先に終了した | 戻り値。起動引数を疑う案内 |
| ポートは待ち受けているが応答しない | プロキシ設定と起動確認URL |
| 何も起きない | 待った秒数と起動確認URL |

どの場合も、ツールの出力ログとランチャーのログの場所を添えます。

### 起動ファイルの文字コード

`.bat` は cmd.exe が**コンソールのコードページ**で、`.vbs` は WSH が**システムANSI**で読みます。
日本語Windowsではどちらも CP932 です。UTF-8 で保存し直すと現場で文字化けします。

`.bat` には順序の決まりもあります。`chcp 932` より前に非ASCIIのバイトがあると、
その部分は違うコードページで解釈されます。CP932 の2バイト目には `0x5C`(`\`)や `0x40`(`@`)が
現れるため、コメントの文字が区切り記号に化けて構文が壊れます。
`tests/test_launch_files.py` が文字コード・改行・この順序を見ています。
